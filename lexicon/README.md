## 每个词条的格式

每个词条是一个二级标题，顺序是：基本信息、通俗释义、核心特征、体验举例（可选）、概念边界、社区定义（没有可写的就不写）。只有基本信息的词条，后面几部分先不写。

### 1. 基本信息

一张两列表格，字段固定，没有内容写"—"：

| 字段 | 写什么 |
|---|---|
| ID | 小写英文加连字符，程序和其他文档靠它引用这个词条，定下后不改 |
| 英文名 | 词条名；有两种拼法并列的用"/"隔开 |
| 中文名 | 中文叫法，括号里注明状态：通行、社群流传、AUREA 中文版、拟。规则见附录 A |
| 别名 | 其他英文叫法、缩写、对应的心动俗称 |
| 层级 | 伞、伞/节点、节点、节点·可叠加、子类、延伸区、对照、概念；图例见 01 的第 0 节 |
| 上位类 | 写上位词条的英文名。这是本稿的组织方式，不代表所有人都这样归类 |
| 对应的轴 | 01 的 2.1 中这个词描述的是哪条修饰轴，或哪个子轴（如 1C、5A） |
| 共识度 | 高 / 中 / 低，含义见 01 的第 0 节 |
| 测试适配度 | A / B / C / D，含义见 01 的第 0 节 |
| 来源 | 定义出自哪里、核到什么程度；链接在附录 B |
| 完成度 | 完整 / 仅基本信息 |

计分怎么判（哪些题、哪些取值）**不写在这里**，只写在 07。

### 2. 通俗释义

写给参与测试的人看的，用通俗的话说明这个词是什么意思。要能单独看懂，不用读完后面几部分才明白。出自哪里、核到什么程度写在基本信息的来源栏，不写进这里。

### 3. 核心特征

不用术语，分 3～4 条讲清楚这个词描述的体验有哪几个要点。开头不加提醒句（作者 2026-10-31 决定），但写法上仍是词义的要点，不写成"满足几条就是"这种自测清单。不写露骨内容，不暗示原因（如"因为受过伤"）。和别的词怎么区分、常见误解，留给概念边界写。具体的画面留给体验举例，核心特征里尽量不举例，免得两处说同一件事。

### 4. 体验举例（可选）

1～3 个贴近日常的具体情境，帮读者想象这个词描述的体验是什么样子。资料少、写不出不走样的情境时，这一部分就不写。

- 写成具体的场景（"喜欢一位歌手很多年……"），不是把核心特征换个说法再讲一遍
- 只演示通俗释义、核心特征和社区定义里已有的内容，不新增条件，也不写"这类人通常会……"这种概括
- 不写露骨内容，不暗示原因
- 开头不加固定的提醒句（作者 2026-10-31 决定）

### 5. 概念边界

- **相似的标签**：表格，列出容易和它混在一起的词，以及区别在哪
- **常见误解**：逐条写，先写误解，再写为什么不对

### 6. 社区定义

社区里怎么定义这个词，排在词条最后（概念边界之后）。只在不同说法确实有出入时写，用读者的话讲出入本身（“有的人用它指……，也有人……”）；没有可写的就不写这一部分。出自哪里、核到什么程度写在基本信息的来源栏，不写进这里；正文禁用的审核用语见文案与词条质量标准第三节的词表（未随公开仓库发布），作者本地的检查脚本会扫。

## 修改规则

- 改定义正文、增删词条，只改这里；迁移完成后，改完要跑 `python3 tools/scoring_data.py build` 重新生成数据
- 网页侧栏里的名词库直接读这里：改完词条跑 `python3 tools/lexicon_data.py build`，重新生成 `web/assets/lexicon.js`。这个脚本只认本文写明的格式（小节、两列表格、列表、引用、粗体小标题）
- ID 定下后不改；词条改名时改英文名，ID 不动
- 新词放哪一类、进主树还是延伸区，按 01 的 2.3 收录规则决定；词从延伸区升进主树时，把整个词条挪到对应文件，ID 不变
- 来源链接仍记在附录 B，这里只写来源的名称和核到的程度
